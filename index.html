1. 제품 입력과 외부 운영의 전달 경계

초기 입력은 단일 제품 사양을 진입점으로 삼습니다. 기존 기능의 폭을 먼저 확인하고 필요한 상세만 부록으로 분리합니다. 과거 코드·요구·승인·완료 상태는 새 개발에 자동 승계하지 않습니다.

이 화면에 설명한 Astra·DDT의 역할과 준비·검토 절차는 팀을 위한 외부 운영 계획입니다. AI-DLC가 읽는 제품 입력에는 포함하지 않습니다.

  • AI-DLC 전달 허용: MindCraft의 목적·사용자·기능·동작·데이터·연계·실행 환경·제품 제약·수용 기준, 필요한 제품 상세 부록과 정제된 제품 질문 답변.
  • AI-DLC 전달 제외: Astra/DDT 명칭·역할, 검토·승인·Git·리포트·인계·clear 절차, 외부 준비 계획·대응표·조사 대장·운영 문서의 경로와 참조.
  • 외부에 저장한 제품 사양은 선택된 본문·부록만 제공하고 외부 하네스 링크가 없는지 확인합니다. 외부 저장 위치를 전체 하네스 탐색 지시로 사용하지 않습니다.
  • AI-DLC가 채택한 제품 요구와 수용 기준은 자체 문서에 반영되어 제품만으로 재개·납품할 수 있어야 합니다.
  • 과거 기능이나 낮은 우선순위만으로 새 범위를 자동 결정하지 않습니다. 범위 결정의 운영 근거는 외부에서 관리합니다.

2. 준비할 파일

아래는 작성 예정 파일입니다. 현재 작성 완료된 것은 준비 계획이며 실제 기능 사양은 아직 없습니다.

제품 입력 사양·필수 제품 상세 부록만 AI-DLC 전달 대상입니다. 조사 기준선·범위 대응표·미결 관리·인계 묶음은 외부 운영용이며 전달하거나 참조시키지 않습니다.

  • 제품 입력 사양 — mindcraft-product-input.md: 목적·사용자·전체 기능 목록·여정·기능별 정상/예외 동작·수용 기준·데이터·실행 조건·최소 품질·미결.
  • 상세 부록 — 기능별 상세가 커질 때만 분리. 진입 사양에 ID·버전·필수 여부를 적고 함께 전달.
  • 조사 기준선 — 기존 제품의 자료·버전, 문서·테스트·실행 관찰, 미조사 영역을 기록. Astra/DDT의 외부 근거로 관리.
  • 범위 대응표 — 기존 기능 후보 → 새 범위 처분 → 전달 사양 → AI-DLC 요구/수용 기준을 연결.
  • 미결 질문 목록 — 질문 ID·영향 기능·현재 근거·답변 주체·해소 시점. 사실 확인과 사용자 결정을 구분.
  • 인계 묶음 — 사양 스냅샷·manifest·질문 맥락·수신 확인. 운영 근거로 보존.

3. 준비 순서와 단계별 결과

  • A. 기준선 조사: 기존 MindCraft 자료 위치와 기준 버전을 특정하고 기능 후보·구현 여부·실행 확인 여부·미조사 영역을 정리합니다.
  • B. 범위 정리: 기능 ID와 사용자 결과·의존성을 부여하고 유지/동등 대체/제외/보류/미결을 근거와 함께 표시합니다.
  • C. 사양 작성: 사용자·트리거·입력·정상 결과·권한·상태 변화·적용 가능한 예외·관찰 가능한 수용 기준을 작성합니다.
  • D. DDT 검토: 실제 스냅샷을 전달해 사실·누락·가정을 검토하고 Astra가 범위·의존성·모순을 대조합니다. 검토 통과와 단계 승인은 별개입니다.
  • E. AI-DLC 전달: 사양 ID·버전·필수 부록을 고정하고 실제 수신을 확인합니다. 미결을 드러낸 분석용 초안으로 질문 단계를 시작할 수 있습니다.
  • F. 반영 확인: AI-DLC 질문을 원문과 사양 ID에 연결해 답변하고, 생성된 요구사항의 기능·예외·수용 기준이 전달 사양을 보존하는지 확인합니다.

4. 사양 작성 시 지킬 기준

  • 제목만 있는 기능은 충분한 사양으로 보지 않습니다. 포함 기능마다 사용자 결과와 판정 가능한 최소 수용 기준을 둡니다.
  • 확정 요구·후보·가정·미결을 구별합니다. 모르는 기능이나 근거 없는 성능 수치를 만들어 확정하지 않습니다.
  • 여러 기능이 연결된 사용자 여정과 실패 흐름을 다룹니다. 적용하지 않는 예외는 이유를 명시합니다.
  • NFR은 Inception에서 목표·검증 방법을 간결하게 정리합니다. Construction의 별도 NFR 단계는 가능한 생략하되 수용 기준과 기능 테스트는 유지합니다.
  • 모듈 간 통신 기능은 계약/API를 먼저 확정한 뒤 모듈별 설계로 진행합니다. 초기 사양에서 내부 구현 구조를 미리 고정하지 않습니다.
  • Security·Resiliency·Property-based testing extension 선택은 AI-DLC의 별도 질문으로 처리합니다. NFR 생략과 extension 비활성화를 혼동하지 않습니다.

  • 실행 링크·데모 미디어는 선택입니다. 체험 경로는 검토하되 배포를 새 필수 요구로 간주하지 않습니다.

6. 준비 완료 판정과 외부 운영

아래 검토·승인·기록·세션 운영 기준은 외부 하네스에서 적용합니다. AI-DLC의 제품 사양에 넣지 않습니다.

  • 전달 전 검사: 제품 사양에 외부 하네스 명칭·역할·운영 규칙·외부 운영 문서 참조가 없는지 확인하고, 전달 파일이 제품 본문·필수 부록·제품 답변으로 한정됐는지 확인합니다.
  • 분석 입력 준비: 기능 ID 중복·상세 누락이 없고 포함 기능의 최소 수용 기준, 범위 처분 근거, 미결, 필수 부록이 명시돼 있어야 합니다.
  • 요구 확정: 관련 미결을 해소 또는 명시적으로 처분하고 AI-DLC 자체 요구사항의 의미·예외·수용 기준 반영을 확인해야 합니다.
  • 전달·수신·반영·구현·실행 검증은 각각 다른 상태로 기록합니다. 문서 작성만으로 기능 완료를 선언하지 않습니다.
  • 단계 종료 시 승인 대상 버전을 특정하고 인계 보존·동기화 후 Claude 세션을 초기화합니다.
  • 공유 자료에는 정제된 요구·결정·승인 사실만 남깁니다. 원시 대화·인증값·내부 추론을 포함하지 않습니다.
  • 무인 자동 진행 준비 여부는 별도 검증 사항입니다. 기록 후 리포트 동기화가 동작하더라도 제품 작성이나 검토가 자동 완료된 것은 아닙니다.
